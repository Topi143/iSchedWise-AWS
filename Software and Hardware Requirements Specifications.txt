I. INTRODUCTION

1.1 Purpose 
The purpose of this document is to define the software and hardware requirements for iSchedWise V4, a web-based scheduling management system designed for educational institutions. The system is being developed to streamline academic scheduling processes, including class and exam scheduling, faculty assignment, and room allocation. The intended users are institutional administrators (Admins), department heads (Deans), and system operators (Super Admins). The system addresses the need for an efficient, conflict-free scheduling tool that replaces error-prone manual scheduling methods, provides real-time conflict detection, and supports data-driven decision-making through AI-powered recommendations.

1.2 Objectives 
The specific objectives of iSchedWise V4 are as follows:
• To automate the creation, modification, and management of class and exam schedules, reducing manual effort and human error.
• To detect and prevent scheduling conflicts (section, faculty, and room overlaps) in real time using built-in conflict detection algorithms.
• To manage faculty workload distribution by tracking unit assignments against configurable maximum unit limits, ensuring balanced and fair workload allocation.
• To optimize room and building utilization by providing visibility into room usage, availability, and capacity.
• To maintain structured curriculum and subject data organized by programs, year levels, and semesters.
• To provide comprehensive reporting and analytics, including the Schedule Quality Index (SQI), faculty workload reports, and room utilization statistics.
• To support data export in Excel (.xlsx) and PDF formats for official documentation and institutional reporting.
• To offer AI-powered scheduling suggestions and conflict explanations via optional Google Gemini API integration.
• To implement a robust archive system that preserves historical schedule data across academic years and semesters.
• To enforce role-based access control, ensuring Deans access only their assigned programs while Admins and Super Admins maintain broader system privileges.

1.3 Scope 
This section defines the boundaries of iSchedWise V4 in terms of features, functions, and limitations. It explains what the system will and will not provide.

• In Scope 
	- Class schedule management (create, edit, delete, archive) with day-of-week and time-based scheduling
	- Exam schedule management with exam period configuration (Prelim, Midterm, Final) and date-specific scheduling
	- Faculty management including workload tracking, subject assignments, and availability configuration
	- Room and building management with capacity tracking and utilization analysis
	- Curriculum and subject management structured by programs, year levels, and semesters
	- Program and department management with section organization
	- Role-based access control for Super Admin, Admin, and Dean roles
	- Conflict detection and prevention for section, faculty, and room overlaps
	- AI-powered scheduling recommendations and conflict explanations (Google Gemini integration)
	- Real-time multi-user coordination via WebSocket (Flask-SocketIO)
	- Comprehensive reporting dashboard with Schedule Quality Index (SQI), workload distribution, and room utilization
	- Excel and PDF export for schedules, faculty lineups, room schedules, and user reports
	- Archive system with soft-delete architecture for historical data retention
	- User authentication with password hashing, session management, and login history tracking
	- Audit logging of all user actions with IP address and timestamp recording
	- Academic settings management (academic year, semester, exam periods, time windows)
	- Institution settings (name, logo) for branding
	- Super Admin tools including maintenance mode, force logout, and system statistics
	- Password reset via email

• Out of Scope 
	- Student enrollment and registration management
	- Grade management and academic transcript generation
	- Tuition and financial management
	- Student portal or student-facing interfaces
	- Learning management system (LMS) integration
	- Mobile application (native iOS/Android)
	- Multi-institution or multi-campus support within a single deployment
	- Automated timetable generation without user input (the system provides recommendations, not fully automated scheduling)

II. Software Requirements Specifications

This section presents the Software Requirements Specification (SRS) of iSchedWise V4, specifically outlining its functional and non-functional requirements. These requirements define what the system must do and how the system must perform under specified conditions.
The functional requirements describe the core features and services that iSchedWise V4 must provide. These include class and exam schedule management, faculty workload tracking, room allocation, conflict detection, AI-powered recommendations, curriculum management, reporting and analytics, data export, user authentication and authorization, archive management, and real-time multi-user coordination.
The non-functional requirements define the quality attributes, performance standards, and operational constraints of iSchedWise V4. These include system security (password hashing, CSRF protection, role-based access), reliability (database rollback on failures, graceful AI degradation), performance (connection pooling, eager loading), and usability (responsive design, fixed-viewport layout).

2.1 Functional Requirements
The following functional requirements define the essential capabilities that iSchedWise V4 must provide:

Authentication and User Management
• The system shall allow users to log in using a username or email address with a hashed password.
• The system shall support three user roles: Super Admin, Admin, and Dean, each with specific access privileges.
• The system shall allow Super Admins to create, edit, archive, and force logout user accounts.
• The system shall support temporary quick-generated user accounts (user### pattern) with 24-hour expiry and a first-login setup flow.
• The system shall provide password reset functionality via email using secure time-limited tokens.
• The system shall track login history including login/logout timestamps, IP addresses, and user agents.
• The system shall allow users to update their profile information (name, email, password).

Class Schedule Management
• The system shall allow authorized users to create, edit, and delete class schedules with the following attributes: day of week, start time, end time, section, subject, faculty, and room.
• The system shall support lecture and laboratory schedule types.
• The system shall organize schedules by academic year and semester.
• The system shall detect scheduling conflicts in real time for section overlaps, faculty double-booking, and room double-booking.
• The system shall implement optimistic locking to prevent concurrent editing conflicts.
• The system shall broadcast real-time schedule updates to connected users via WebSocket.

Exam Schedule Management
• The system shall allow authorized users to create, edit, and delete exam schedules with date-specific scheduling.
• The system shall support exam period configuration (Prelim, Midterm, Final) with date range validation.
• The system shall enforce configurable exam slot durations (30, 60, 90, or 120 minutes) and maximum exam duration limits.
• The system shall configure lunch break periods for exam scheduling.
• The system shall verify faculty availability when assigning exam proctors.

Faculty Management
• The system shall allow authorized users to create, edit, and archive faculty profiles.
• The system shall track faculty subject assignments per academic year and semester.
• The system shall calculate and display faculty workload as a percentage of their maximum unit limit.
• The system shall provide configurable maximum unit limits per individual faculty and a system-wide default.
• The system shall display workload status badges (normal, warning, exceeded).
• The system shall allow configuration of faculty availability by day and time.

Room and Building Management
• The system shall allow authorized users to create, edit, and archive buildings and rooms.
• The system shall track room capacity for each room.
• The system shall link rooms to their parent buildings.
• The system shall provide room utilization reports showing occupancy and availability.

Curriculum and Subject Management
• The system shall support curriculum creation organized by program, year level (1st through 4th year), and semester (1st, 2nd, Summer).
• The system shall manage subjects with attributes including subject code, description, total units, lecture hours, lab hours, credit units, and prerequisites.
• The system shall support subject templates to reduce data duplication across curricula.

Program and Section Management
• The system shall allow authorized users to create, edit, and archive academic programs linked to departments.
• The system shall manage student sections within programs.
• The system shall restrict Dean users to view and manage only their assigned programs.

Archive System
• The system shall implement soft-delete architecture using is_archived and is_active flags on main tables.
• The system shall record archive metadata including archived_by, archived_at, and archive_reason.
• The system shall automatically archive schedules when academic settings (year/semester) change.
• The system shall support unarchiving of previously archived records.
• The system shall allow browsing of archived data filtered by academic year, semester, and exam period.

Reports and Analytics
• The system shall provide a reports dashboard displaying schedule counts, faculty workload analysis, room utilization statistics, and weekly activity trends.
• The system shall calculate and display a Schedule Quality Index (SQI) as a three-metric composite score.
• The system shall generate faculty workload distribution reports by department.
• The system shall generate room utilization reports showing peak usage hours and availability.
• The system shall restrict Dean users to reports for their assigned programs only.

Export Capabilities
• The system shall export class schedules, faculty schedules, room schedules, faculty lineups, and user lists in Excel (.xlsx) format with formatted headers, colors, borders, and alignment.
• The system shall export class schedules, faculty schedules, room schedules, and user reports in PDF format with institution branding (name, logo).
• The system shall include timestamps and user information on all exports.

AI-Powered Decision Support
• The system shall detect scheduling conflicts using built-in Python algorithms (no external API required) with severity levels: Critical, High, Medium, and Low.
• The system shall provide smart recommendations for alternative time slots, days, rooms, and faculty with workload-aware ranking.
• The system shall optionally integrate with Google Gemini API (gemini-2.5-flash model) for natural language conflict explanations and scheduling advice.
• The system shall gracefully degrade to built-in algorithms if the Gemini API is unavailable.

Academic and Institution Settings
• The system shall allow configuration of academic year, semester, and exam period.
• The system shall allow configuration of schedule and exam time windows (start/end hours).
• The system shall allow configuration of exam parameters (lunch break times, slot duration, maximum duration).
• The system shall allow configuration of institution name and logo for report branding.

System Administration
• The system shall provide a Super Admin panel with system statistics, recent activity feed, and system information.
• The system shall support maintenance mode that blocks non-Super-Admin users with a custom message.
• The system shall allow Super Admins to force logout specific users.
• The system shall log all user actions (create, edit, delete, archive) with entity type, entity ID, IP address, user agent, and timestamp.

2.2 Non-Functional Requirements

Security
• The system shall hash all user passwords using Werkzeug's security module (not stored in plain text).
• The system shall enforce password length validation (8–30 characters).
• The system shall implement CSRF token validation on all forms using Flask-WTF.
• The system shall prevent SQL injection through the use of SQLAlchemy ORM parameterized queries.
• The system shall enforce role-based access control (RBAC) using @login_required and @role_required decorators on all protected routes.
• The system shall restrict Dean users to data within their assigned programs and departments only.
• The system shall log all authentication events including login attempts, IP addresses, and user agents.
• The system shall support secure password reset tokens with a 1-hour expiration period.
• The system shall manage API keys (Gemini) through environment variables, not hardcoded in source code.

Reliability
• The system shall perform automatic database rollback on transaction failures to maintain data integrity.
• The system shall enforce foreign key constraints with appropriate ON DELETE behavior (SET NULL, CASCADE).
• The system shall provide graceful degradation when the optional Gemini AI API is unavailable, falling back to built-in Python algorithms.
• The system shall implement maintenance mode to prevent accidental modifications during system updates.
• The system shall use optimistic locking to detect and handle concurrent edit conflicts.
• The system shall validate all schedule data against configurable time windows and academic settings before saving.

IV. OVERALL DESCRIPTION

4.1 Summary
iSchedWise V4 is a web-based scheduling management system designed for educational institutions. It enables administrators and department heads to create, manage, and optimize class and exam schedules while tracking faculty workloads, room utilization, and curriculum structures. The system features intelligent conflict detection, AI-powered scheduling recommendations, role-based access control, comprehensive reporting with a Schedule Quality Index (SQI), and data export capabilities in Excel and PDF formats. Built with Flask and MySQL, it provides real-time multi-user coordination through WebSocket technology and maintains historical scheduling data through an archive system.

4.2 User Characteristics
The following user roles are expected to interact with iSchedWise V4:

Super Administrator
• Background: IT staff or designated system operator responsible for overall system maintenance
• Technical Proficiency: Moderate to high — familiar with web application administration, database management, and system configuration
• Responsibilities: Full system access including user management, maintenance mode, force logout, system statistics monitoring, and institution settings configuration
• Training Required: System administration training, understanding of academic scheduling processes

Administrator (Admin)
• Background: Institutional staff responsible for campus-wide academic scheduling
• Technical Proficiency: Moderate — comfortable with web-based applications and office productivity tools
• Responsibilities: Managing all scheduling operations, faculty assignments, room allocation, curriculum management, program management, report generation, and data exports
• Training Required: Application orientation, scheduling workflow training, export and reporting capabilities

Dean (Department Head)
• Background: Academic department head overseeing scheduling for their assigned programs
• Technical Proficiency: Basic to moderate — general familiarity with web browsers and standard office applications
• Responsibilities: Viewing and managing schedules, faculty, and curricula within their assigned programs; generating program-specific reports
• Training Required: Basic application orientation focused on department-specific workflows

The system shall accommodate users with varying levels of expertise through an intuitive fixed-sidebar navigation layout, role-appropriate dashboards, confirmation modals for critical actions, toast notifications for feedback, and minimal learning curve design principles.

4.3 Use Case Scenarios

Use Case 1: Creating a Class Schedule
Actor: Admin
Precondition: Academic year, semester, sections, subjects, faculty, and rooms are configured.
Flow: The Admin navigates to the Class Schedule page, clicks "Add Schedule," selects the section, subject, faculty, room, day, and time, and submits the form. The system checks for conflicts (section overlap, faculty double-booking, room double-booking) in real time. If no conflicts exist, the schedule is saved and broadcast to connected users via WebSocket. If conflicts are detected, the system displays severity-rated warnings and provides AI-powered alternative recommendations.

Use Case 2: Managing Faculty Workload
Actor: Admin/Dean
Precondition: Faculty profiles and subject assignments exist.
Flow: The user navigates to the Faculty page and views the workload summary showing each faculty member's assigned units versus their maximum unit limit. Workload status badges (normal, warning, exceeded) are displayed. The user can click on a faculty member to view detailed assignments, adjust maximum unit limits, or reassign subjects.

Use Case 3: Generating Reports
Actor: Admin/Dean
Precondition: Schedules exist for the current academic year and semester.
Flow: The user navigates to the Reports page and views the dashboard displaying schedule counts, faculty workload distribution, room utilization statistics, and the Schedule Quality Index (SQI). The user can filter data by department or program (Deans see only their assigned programs). The user exports the desired report as Excel or PDF.

Use Case 4: Archiving Schedules
Actor: Admin/Super Admin
Precondition: Schedules exist for a completed academic period.
Flow: When the Admin changes the academic year or semester in Settings, the system automatically archives all current schedules with metadata (archived_by, archived_at). Archived schedules can be browsed and exported from the Archive page, filtered by academic year, semester, and exam period.

Use Case 5: Exam Scheduling
Actor: Admin
Precondition: Exam period is configured with date ranges, and class schedules exist.
Flow: The Admin navigates to the Exam Schedule page, configures the exam period (Prelim/Midterm/Final) with start and end dates, and creates exam schedules with specific dates, times, sections, subjects, proctoring faculty, and rooms. The system validates against exam time windows, lunch breaks, slot durations, and checks for faculty availability conflicts.
